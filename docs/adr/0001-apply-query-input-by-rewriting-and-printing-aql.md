# Apply a query's structured input by rewriting the AQL AST and printing it back

The Anfra SDK sends each query as AQL plus structured input: control filters, cross-filter conditions, sorts, date drills and paging. anfra only runs AQL. We apply the input in `amql` (hcore) by parsing the AQL, rewriting the explore node, and printing the result back to AQL text, which anfra-node then compiles as usual. We chose this over two alternatives. Rewriting the AST and compiling it directly would skip printing, but we need the executed AQL anyway so the query can be inspected. hdev's approach, compiling to a VizSetting, injecting there and converting back, would drag in the viz layer. This means amql must ship a printer that round-trips the AST exactly (comments are not preserved). Paging and timezone are not AQL. The timezone is the existing `timezoneRegion` compile option. Paging is applied by anfra-node where it runs SQL generation, by setting the outermost limit/offset on the compiled query; it isn't an amql compile option (the amql author's call). A pivot's compiled query isn't one flat result set: one grid row spans many SQL rows, and header rows come first, so LIMIT/OFFSET would split it. anfra-node therefore rejects paging on a pivot query ("Pagination for pivot queries isn't supported yet."). Paging is opt-in in the Anfra SDK: only a query that declares a `pageSize` sends a page, and one that doesn't gets every row. So a Data App can run a pivot query as long as it doesn't page it. Paging a pivot by filtering its `__pivot_row__`/`__pivot_column__` ranks, as hdev's sort-before-limit does, is the way in if it's ever needed.
